## 控制台步骤

1. 进入上述服务的“部署发布”，点击“发布”。
2. 选择方式保留“绑定 GitHub 仓库”，仓库选择 `marinelj/hoopformer`，分支选择 `codex/wechat-cloud-deployment`。此部署分支以当前 `main` 为基础，加入了部署文件和派生模型。
3. 将端口 80 改为 **8000**。在高级设置中，若出现 Dockerfile 路径和构建目录，分别使用 `Dockerfile` 和仓库根目录。已有资源规格保持不变；内存比赛状态只支持一个实例。
4. 发布后等待构建、启动和版本切换成功。仅上传代码或创建版本成功不代表新版本已在线；旧模板没有 `/api/new` 比赛接口。
5. 在小程序重新连接，应看到 90年代全明星 对 00年代全明星。开始比赛并检查回合、记分牌和中文指令。

## 镜像依赖修正（2026-10-09）

首次云端日志表明镜像构建已完成，但大小为 9.6GB：原 Dockerfile 安装了研究项目的完整依赖，包括 PyTorch 和其 CUDA/NVIDIA 库。当前比赛服务使用预先计算的球员概率，没有 PyTorch 推理。

Dockerfile 现改用 `deploy/tencent/pyproject.toml` 的运行依赖配置，保留 CLI 所需的数据/统计库，排除 PyTorch、CUDA 和 NVIDIA 训练库。根目录研究配置保留原样。可在独立 Python 环境安装此配置，然后以该环境运行真实比赛接口测试；这不等同于 Linux 镜像大小测量。重新执行现有部署分支的流水线时会读取这项修改。

容器同时明确设置 `PYTHONPATH=/app/src`。网页资产路径按源代码位置定位；从安装的 site-packages 加载模块会指向错误目录。部署测试现读取 Dockerfile 的环境变量并调用实际安装的 `hoopformer` 命令，不再只通过测试自行设置的源代码路径启动。

## 模型与密钥

`models/` 只包含两个运行所需的派生 JSON 和 SHA-256 来源说明，不包含原始 NBA 响应。模型使用真实缓存的 2025-26 数据，加上经典球员派生资料，含 606 名球员和 32 支球队；不声称包含 2026-27 阵容。经典球员的人工假设与测量范围见 `docs/GAME_DESIGN.md`。

无 API key 时规则指令仍能工作。需要自由中文自然语言理解时，由管理员在云服务环境变量配置已有的 `DASHSCOPE_API_KEY` 或 `OPENAI_API_KEY`。密钥不在仓库、镜像或聊天中填写。

每局比赛使用独立 game_id，电脑与手机不再覆盖彼此。会话保存在单实例内存，最多 32 局，空闲两小时失效；重启会丢失，仍要求单实例。

## 手机问题修复（2026-10-09）

此版本修复五人卡片数组损坏、英文残留、失败原因被隐藏、战术失败未回滚，并为手机加入运球、进球、打铁和蜂鸣音效及声音开关。API 返回 game_id，两个客户端后续请求携带该编号；升级后端和小程序预览才能获得会话隔离。仍保持 8000 端口和单实例。

真实开发者工具已经通过连续球员指令、战术/角色、暂停/恢复、音效播放回调，以及真实会话过期后的回滚和重新开赛。音效文件检查了 PCM 振幅、时长和削波；手机音量与真实麦克风转写仍需手机验证。
